# TM1703: GPIO и runtime PM дискретной GPU

Дата измерения: 2026-10-26

## Метод

Измерения выполнены на заводском BIOS Insyde `XMAKB3M0P1710` под Linux с
драйвером `nouveau`. GPU `10de:1d12` находится на `01:00.0` за RP1
`00:1c.0`, PCIe x4.

Использовался штатный runtime PM:

- `power/control=on`, затем `inteltool -g`;
- `power/control=auto`, ожидание `runtime_status=suspended`, затем
  `inteltool -g`;
- повторный `power/control=on` и второй снимок.

В конце `power/control` восстановлен в `auto`. SPI, ME/HECI и firmware не
изменялись.

## Воспроизводимость

```text
active-1: 3c4684051a297a42b41a80429b5a403c462ffc8f41226d3c0119fed71065cad1
suspended: 1d8990bd6e921f6f2184ea0c225a96aa6aa9c22c7481f954599ccb2d4c648e87
active-2: 3c4684051a297a42b41a80429b5a403c462ffc8f41226d3c0119fed71065cad1
```

Оба active-снимка побайтно одинаковы. Переход в autosuspend занял 7 секунд.

## Изменяющиеся pads

Между active и suspended меняются только четыре строки:

```text
                    active              suspended
GPP_B5 CLKREQ0#     0x3544000700        0x3544000702
GPP_G1 GPIO output  0x4984000201        0x4984000200
GPP_G3 GPIO input   0x4b84000102        0x4b84000100
GPP_G4 GPIO output  0x4c84000200        0x4c84000201
```

Обратный переход изменяет те же биты в обратном направлении. Конфигурация
pad не меняется; меняются только RX/TX state bits.

Наблюдаемая логика:

- `GPP_B5 / SRCCLKREQ0#` asserted при active GPU;
- `GPP_G1` устанавливается в `1` при active GPU;
- `GPP_G3` как вход показывает `1` при active GPU;
- `GPP_G4` устанавливается в `0` при active GPU.

Это clean-room наблюдение поведения оборудования. Функциональные имена
board-specific сигналов пока не назначаются: для подтверждения power-enable,
power-good и reset нужны временная последовательность или измерения.

## Следствия для coreboot

- RP1 использует `CLKREQ0#`, следовательно,
  `PcieRpClkReqNumber[0]` должен быть `0`, а не текущее значение `2`.
- Номер clock source этим измерением не определяется. Текущее значение
  `PcieRpClkSrcNumber[0] = 2` совпадает с Kaby Lake FSP/RVP reference default,
  но остаётся отдельно подтверждаемым параметром.
- Для включённой во время PCI scan GPU устойчивые уровни равны:
  `GPP_G1=1`, `GPP_G3=1` (input observation), `GPP_G4=0`.
- Нельзя программировать только конечные уровни без проверки порядка:
  безопасная power/reset sequence пока не подтверждена.

## Дополнительный SSH-сбор: 26 октября 2026

Сняты согласованные snapshots на OEM-системе по SSH при переключении только
runtime PM GPU; системный сон не использовался. После измерения исходное
`power/control=auto` и `runtime_status=suspended` восстановлены.

```text
pad       active                                      suspended
GPP_G1    0x4984000201 (GPIO output, value=1)        0x4984000200 (value=0)
GPP_G3    0x4b84000102 (GPIO input, value=1)         0x4b84000100 (value=0)
GPP_G4    0x4c84000200 (GPIO output, value=0)        0x4c84000201 (value=1)
GPP_B5    0x3544000700 (SRCCLKREQ0#, state=0)        0x3544000702 (state=2)
GPP_B11   0x3b44000700 (EXT_PWR_GATE#, unchanged)   0x3b44000700 (unchanged)
```

Это подтверждает, что GPP_G1/G3/G4 — динамические линии runtime PM, а GPP_B11
в этом переходе не меняется и не может быть назначен runtime GPU power-enable
на основании данного эксперимента. Снимки достаточны для описания pad-режимов
и active/suspended уровней, но не для восстановления ранней boot-последовательности:
порядок включения питания, power-good и снятия `PERST#` по-прежнему не измерен.

## Наблюдения по Wi-Fi и NVMe

Дополнительный read-only сбор подтвердил топологию и эксплуатационные
ограничения:

- единственный сетевой интерфейс `wlp2s0` находится на RP5 (`02:00.0`, Intel
  Wireless 8265); через него идёт SSH-соединение;
- корневая файловая система находится на NVMe `03:00.0` за RP9;
- оба устройства работают с `power/control=on`, поэтому принудительный
  runtime suspend по SSH не выполнялся;
- RP5 и RP9 включены как ACPI wake sources;
- у RP5 линк PCIe Gen1 x1, у RP9 — PCIe Gen3 x4; на обоих OEM BIOS включает
  ASPM L1.

Во всех трёх доступных снимках работающей OEM-системы состояние native
CLKREQ pads одинаково:

```text
GPP_B5 / CLKREQ0# = deasserted, когда NVIDIA suspended
GPP_B6 / CLKREQ1# = deasserted
GPP_B7 / CLKREQ2# = asserted
```

Так как NVMe за RP9 остаётся активным, `CLKREQ2#` является сильным кандидатом
на его CLKREQ. Это пока корреляция, а не окончательное доказательство. Она
показывает, что текущее значение `PcieRpClkReqNumber[8] = 5`, взятое из FSP
reference defaults, нельзя считать конфигурацией TM1703. Для RP5 доступные
снимки не позволяют надёжно подтвердить либо исключить `CLKREQ1#`.

Номера clock source этими GPIO-наблюдениями не определяются.

## Open-source FIA reference

Для независимой проверки использована последняя открытая ревизия
`KabylakeSiliconPkg` перед её удалением из официального репозитория Tianocore
`edk2-platforms`:

```text
repository: https://github.com/tianocore/edk2-platforms.git
commit:     09608a9ad5582b5084de7548c9b1aa7c4bdd2570
```

Исходники определяют FIA как PCR port `0xcf`, а соответствие root port к
CLKREQ хранится в регистрах `DRCRM1..4` по адресам `0x100..0x10c`. На каждый
root port приходится четырёхбитное поле; нулевое кодированное значение
означает отсутствие CLKREQ. Функция `GetPortClkReqNumber()` читает эти поля
непосредственно из FIA.

Регистры могут независимо и без анализа OEM-кода дать точную карту CLKREQ
всех root ports. Однако полный снимок `inteltool --pcr=0xcf` применять нельзя:
26 октября 2026 года он жёстко завис на OEM-системе. Реализация `inteltool`
последовательно читает весь 64-КиБ PCR-порт (`0x0000..0xfffc`), хотя для этой
задачи нужны только `DRCRM1..4` и `LOS1..4`. После аппаратного выключения
ноутбук загрузился нормально, P2SB снова был скрыт. Для дальнейшего сбора
допустим только отдельно рассмотренный точечный reader нужных регистров.
Эти регистры не содержат номер физического clock source, поэтому CLKSRC
остаётся отдельной задачей.

Точечное чтение через уже настроенный MMIO BAR, без раскрытия P2SB:

```text
FIA.DRCRM1 (0xfdcf0100) = 0x00010000
```

Система после чтения осталась отзывчивой. Восемь четырёхбитных полей DRCRM1
описывают физические RP1--RP8; код `0` означает отсутствие CLKREQ, а код `1`
соответствует `CLKREQ0`. Таким образом, единственное назначение в DRCRM1 —
физический `RP5 -> CLKREQ0`. FSP в эксперименте f25 обнаружил на физическом
RP5 Wi-Fi, поэтому это назначение относится к Wi-Fi; физический RP1 с NVIDIA
не имеет FSP-managed CLKREQ.

Второе точечное чтение также прошло без зависания:

```text
FIA.DRCRM2 (0xfdcf0104) = 0x00002222
```

Код `2` назначен физическим RP9--RP12, что соответствует четырём линиям x4
NVMe. FSP UPD принимает номера CLKREQ `0..6`, тогда как EDK2 определяет
DRCRM-код `0` как отсутствие CLKREQ; отсюда следует односмещённое аппаратное
кодирование, и `2` означает `CLKREQ1`. Итого подтверждённая карта:

```text
physical RP5       -> CLKREQ0 (Wi-Fi)
physical RP9-RP12  -> CLKREQ1 (x4 NVMe group)
physical RP1       -> no FSP-managed CLKREQ (NVIDIA)
```

Ранее наблюдавшееся изменение `GPP_B5/CLKREQ0` одновременно с runtime PM
NVIDIA теперь нельзя считать достаточным доказательством прямой связи этого
сигнала с GPU: оно противоречит прямой FIA-карте и требует отдельного
объяснения или повторного контролируемого измерения.

Debugfs также подтвердил, что на OEM-системе только `GPP_B5..B7` находятся в
native-режиме `SRCCLKREQ0#..2#`. `GPP_B8..B10`, соответствующие
`SRCCLKREQ3#..5#`, настроены как обычные GPIO. Поэтому текущие настройки
`RP5 -> CLKREQ3` и `RP9 -> CLKREQ5`, скопированные из FSP sample defaults,
не могут описывать разводку TM1703.

## Следующий сбор без SPI

Для определения порядка нужны измерения `GPP_G1`, `GPP_G3` и `GPP_G4`
логическим анализатором при обычном runtime resume/suspend. Если это
невозможно, допустим консервативный эксперимент: сначала enable, ожидание
power-good input, затем deassert предполагаемого reset; выключение — в
обратном порядке. Такой эксперимент требует отдельного аппаратного ревью до
прошивки.

# TM1703: правила работы

## Сборки и прошивка

- Каждая сборка, которая идёт на прошивку, = отдельный коммит в ветке `wip/bringup`
  с сообщением `<эпоха>NN: <что изменено>`. Сначала коммит, потом сборка.
- В `.config` выставлять соответствующий `CONFIG_LOCALVERSION="<эпоха>NN"`,
  чтобы номер был в баннере лога.
- Текущие обозначения эпох:
  - `e` — **Establishing Execution**: первичный запуск и инициализация ОЗУ;
  - `f` — **Firmware Foundations**: штатные CPU/MP/VMX/MTRR, FSP/ME,
    payload и стабильная базовая загрузка;
  - `g` — **GPIO Groundwork**: восстановление и проверка полной GPIO-таблицы.
- Номер эпохи присваивается только образу, реально предназначенному для
  прошивки. Документация, lint-исправления и иные непрошиваемые подготовительные
  коммиты номера аппаратной итерации не получают.
- Изменения вне `src/mainboard/xiaomi/tm1703` - отдельными коммитами с префиксом
  `HACK:` и объяснением, зачем они нужны и как проверить, что ещё нужны.
- Никогда не делать `git checkout`/`git restore`/`git reset --hard` по незакоммиченным
  изменениям без явного подтверждения.
- Сохранять flashconsole-лог каждой сборки в
  `work-in-progress/logs/<эпоха>NN.log`.
- Коммиты, подготовленные с помощью AI, должны содержать честный trailer
  `Co-authored-by:`. Для текущего помощника используется
  `Co-authored-by: Codex <noreply@openai.com>`.

## Необходимые общие изменения

- Flashconsole использует общие буфер, смещение и SPI-контроллер без
  синхронизации. В ramstage писать и сбрасывать её буфер разрешено только BSP;
  вывод AP в flashconsole должен отбрасываться. BSP-only поведение считается
  необходимым исправлением, подтверждённым на железе, а не временным обходом
  порта.
- Не перечислять BSP-only flashconsole среди оставшихся временных изменений в
  обычных итогах отдельных итераций. Подсвечивать изменение отдельно только
  когда оно непосредственно относится к результату теста или проводится
  полный аудит кодовой базы.

## Аудиты между этапами

- Предлагать полный аудит итогового diff и истории временных изменений при
  переходе от одной глобальной цели roadmap к следующей.
- Во время такого аудита отдельно проверять все изменения вне
  `src/mainboard/xiaomi/tm1703`, включая необходимый BSP-only патч
  flashconsole, общие Kconfig/Makefile изменения и отсутствие забытых
  диагностических обходов.
- Между вехами не повторять полный перечень уже принятых общих изменений без
  новой причины; текущие итерации должны оставаться сфокусированными на своей
  проверяемой гипотезе.

## Закрытые бинарники и история

- Новые закрытые OEM-бинарники в Git не добавлять. IFD, ME и EC получать
  локально из пользовательского дампа по инструкции `TM1703-BLOBS.md`.
- VBT является допустимым для поставки board-specific data-файлом coreboot и
  хранится в `src/mainboard/xiaomi/tm1703/data.vbt`. Не относить его к
  непоставляемым IFD, ME и EC.
- IFD и ME извлекать штатным `util/ifdtool`; для VBT использовать
  `util/intelvbttool`, когда исходником служит Intel Option ROM, а также для
  проверки и разбора уже извлечённого VBT. Не заменять эти утилиты ручной
  нарезкой по фиксированным смещениям без необходимости.
- Наличие таких файлов в старых коммитах временно принято и не блокирует новые
  этапы разработки или обычный `git push`.
- Очистку и переписывание опубликованной истории выполнять позже как отдельную
  явно согласованную операцию; не напоминать о ней в каждой итерации.

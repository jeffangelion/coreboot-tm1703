# TM1703: правила безопасности

## ME, HECI и Intel Boot Guard

- Не выполнять команды, обращающиеся к ME через HECI.
- Не запускать `CLOSEMNF`, `fpt`, `meinfo`, `mei-amt-check` и другие ME-утилиты.
- Не загружать модули `mei` и `mei_me` и не открывать `/dev/mei*`.
- Не изменять ME, IFD или дескриптор без проверенного способа восстановления.
- Перед любыми действиями с прошивкой проверять `sudo intelmetool -b`.
- `Boot Guard MSR Output` должен оставаться `0x0`. При любом изменении остановиться.

### Явные исключения

Следующие действия допускаются только как часть штатной загрузки coreboot и не считаются разрешением на произвольное взаимодействие с ME:

- `cse_init()` в romstage: назначение временного HECI BAR и аппаратный HECI reset, необходимые для инициализации платформы;
- отправка штатного `DRAM Init Done` (`SendDidMsg`) из Intel FSP после успешной инициализации памяти;
- отправка штатного `ChipsetInit` из Intel FSP допускается только отдельным контролируемым тестом, с неизменными IFD/ME-регионами и проверкой Boot Guard до и после теста;
- отправка coreboot диагностической MKHI-команды `GET_FW_VERSION` разрешена только для чтения версии ME во время штатной загрузки; команда не должна использоваться как разрешение на другие MKHI-запросы или изменение состояния ME;
- отправка coreboot штатной MKHI-команды `GLOBAL_RESET_REQ` разрешена только для выполнения global reset, уже запрошенного возвращённым статусом Intel FSP `FSP_STATUS_RESET_REQUIRED_*`; исключение не разрешает произвольные запросы сброса ME;
- отправка штатного `End of Post` (EOP) из Intel FSP разрешена в рамках
  обычной загрузки coreboot; EOP завершает BIOS-фазу протокола с ME и не
  является командой `CLOSEMNF`, разрешением на запись FPF или закрытие
  Manufacturing Mode;
- чтение PCI-конфигурации и регистров состояния, необходимое для диагностики, если оно не открывает `/dev/mei*` и не отправляет HECI-команды.

Эти исключения не разрешают другие MKHI/HECI-транзакции. По-прежнему
запрещены `CLOSEMNF`, `HMRFPO`, запись FPF и команды закрытия Manufacturing
Mode. Исключение не распространяется на `fpt`, `meinfo`, `mei-amt-check`,
fwupd и другие внешние ME-утилиты.

Резервный SPI-дамп восстанавливает только содержимое SPI-flash. Он не может отменить прожиг FPF, поэтому ни DID, ни ChipsetInit не считаются разрешением на операции с FPF.

## Обновления и прошивка

- Не использовать OEM BIOS-флешеры, BIOS-update ISO и чужие UEFI-капсулы.
- Не использовать `fwupd` для обновления прошивки.
- Не загружать Windows с автоматическими обновлениями firmware и не устанавливать Xiaomi-утилиты.
- Запись выполнять внешним программатором T48 или через `flashrom -p internal`.
- Перед первой записью сделать эталонный дамп T48 и сравнить его хеш с исходным дампом.

## Проверка coreboot-образа

- Перед прошивкой проверять IFD/ME/EC/CBFS-разметку.
- Проверять хеш и размер EC-файла.
- Проверять, что EC находится по смещению `FLREG1` (в стандартной разметке `0x900000–0x93ffff`, либо `0x120000–0x15ffff` при использовании усечённой разметки `board_me_truncated.fmd`).
- Проверять исходники и образ на нежелательные строки и вызовы:
  `heci`, `mkhi`, `closemnf`, `hmrfpo`, `fpf`.
- Не считать успешную сборку доказательством работоспособности на железе.

## Flashconsole

- Flashconsole разрешён только для диагностики при отсутствии UART.
- Его область не должна пересекаться с IFD, ME, EC или CBFS.
- Flashconsole пишет журнал в SPI-flash и может вызывать износ памяти.
- После получения нужного лога не выполнять лишние циклы записи.
- Лог извлекать внешним программатором или штатным чтением FMAP-области.

## SSH и sudo

- Read-only сбор диагностической информации по SSH разрешён.
- Любая `sudo`-команда выполняется только после отдельного одобрения пользователя.
- Не выполнять полный дамп FIA командой `inteltool --pcr=0xcf`: на TM1703
  команда воспроизводимо не проверена и уже вызвала жёсткое зависание системы.
  Любое следующее чтение PCR должно быть ограничено заранее известными
  регистрами и отдельно согласовано.

## Clean-room engineering

- Не дизассемблировать и не декомпилировать OEM firmware: не использовать
  IDA, Ghidra, `objdump -d` и аналогичные инструменты для исследования
  исполняемого кода заводского BIOS или EC.
- Не переносить в реализацию сведения, полученные из уже выполненной
  декомпиляции OEM-кода, пока они не будут независимо подтверждены разрешённым
  источником.
- Разрешённые источники: опубликованные исходники coreboot и EDK2, публичная
  документация и заголовки Intel/FSP, схемы или boardview с допустимым
  происхождением, а также наблюдаемое состояние и поведение собственного
  оборудования (`inteltool`, PCI/USB/I2C/ACPI-интерфейсы ОС, измерения и
  контролируемые тесты).
- Структурный разбор собственных firmware-дампов допускается только для
  извлечения данных и стандартных контейнеров (IFD/FMAP/CBFS, SPD, VBT и ACPI
  tables), но не для анализа исполняемого OEM-кода.
- Для каждого board-specific параметра сохранять происхождение. Если чистый
  источник не найден, параметр считать неподтверждённым и не выдавать за
  clean-room результат.
- Если потребуется классическая clean-room схема, анализ оригинала и
  реализацию должны выполнять разные участники; реализатор получает только
  функциональную спецификацию без OEM-кода и декомпиляции.

## Запрет необратимых действий

Нельзя провоцировать закрытие Manufacturing Mode. Необратимая активация Intel Boot Guard может запретить запуск неподписанного coreboot и сделать восстановление ноутбука невозможным без аппаратного программатора.
